# Konnichiwa Reservations — Disaster Recovery Runbook

Authority: R1.4 Operational Resilience (Chief Engineer Implementation Instruction, BR-R14-01–04). Architecture basis: `R1_4_OPERATIONAL_RESILIENCE_ARCHITECTURE.md`. Implementation evidence: `R1_4_OPERATIONAL_RESILIENCE_IMPLEMENTATION_REPORT.md`.

**Recovery authority: OWNER ONLY.** Nobody else may authorize a production database restore, declare disaster recovery active, or declare a restored database authoritative (BR-R14-04). Managers may activate and run the manual operational fallback (§2 below) and coordinate reconciliation (§4), but never the database-level recovery actions in §3.

This runbook has two independent halves that must not be conflated:

- **§2 — Restaurant continuity during the outage** (what staff do, right now, with no database access).
- **§3 — Database recovery** (what the Owner, or an Owner-delegated technical operator, does to bring the system itself back).

They can and usually will run in parallel — staff should not wait for §3 to finish before starting §2.

---

## 1. Incident Declaration

Anyone who notices the reservation system is unavailable or clearly wrong should say so immediately (whoever is on shift). Only the **Owner** declares this a disaster-recovery incident and decides whether §3 is needed — a brief outage that resolves itself (§ F1/F3 in the architecture report) may not require it. If in doubt, start §2 anyway — it costs nothing to have a paper trail running, and stopping it once the system is confirmed healthy is trivial.

---

## 2. Restaurant Continuity During the Outage (Manager-activatable, staff-executed)

**A Manager may declare the manual operational fallback active** without waiting for Owner sign-off — restaurant service should not stall on a database-recovery decision.

### 2.1 Consult the latest service snapshot

Look at `snapshots/latest.html` (generated by `npm run service-snapshot` — see its embedded "Generated:" timestamp for how current it is). This is a **read-only operational contingency artifact, not the live system and not a database backup** — it shows the next 48 hours of Proposed/Confirmed reservations (guest name, phone/email, party size, area, table, notes, status) and nothing else. It was NOT designed to be authoritative once the system returns — see §4.

If no snapshot exists or it looks badly stale, proceed on the most recent knowledge staff have (memory, a phone callback list, whatever exists) — do not wait for a snapshot that isn't there.

### 2.2 Record every change on paper (or any offline tool) during the outage

For **every** new reservation, cancellation, modification, or walk-in taken while the system is down, record at minimum:

| Field | Notes |
|---|---|
| Guest name | |
| Phone or email | At least one — same minimum as CAP-D05.01-R01 |
| Date/time | |
| Party size | |
| Area (Sushi/Teppanyaki) | If known/relevant |
| Allergies/critical note | Only if operationally necessary — do not over-collect |
| Type | New reservation / Modification / Cancellation / Walk-in |
| Time recorded | So order-of-events can be reconstructed later |
| Staff member recording it | For accountability and follow-up questions |

**Do not invent automated capacity authority while the system is offline.** Nobody has live visibility into exact remaining capacity — every acceptance decision during the outage is a manual, staff-judgment call, same as it would be without any reservation system at all. When in real doubt, prefer holding a slot open (turn away rather than double-book) — false negatives are recoverable at reconciliation; false positives (double-booked slots) are not.

### 2.3 Who decides when normal operation resumes

The **Owner** declares the restored/recovered system authoritative (§3.7) — staff should keep using the manual fallback until that explicit declaration, even if the app appears to be responding again (it may be up but not yet verified, per §3.5's integrity check).

## 3. Database Recovery (Owner-only authorization)

### 3.1 Determine failure type

Map the observed symptom against the architecture report's F1–F10 taxonomy before choosing a response:

- **App down, DB fine (F1)** — restart the process (`npm start`). No restore needed.
- **DB temporarily unreachable (F3)** — wait/investigate the local PostgreSQL instance; `GET /health` does NOT check DB connectivity (a known gap — see architecture report §6/F3), so a 200 from `/health` does not mean the database is fine.
- **DB completely lost (F4), or logical corruption/bad migration/accidental delete (F5/F6/F7)** — proceed with restore, §3.2 onward.
- **Backup itself missing/corrupt (F8)** — see §3.2's backup-selection step; do not attempt to restore a backup whose manifest shows `"status": "FAILED"` or whose checksum cannot be re-verified.

### 3.2 Select a recovery point

List backups in `backups/` (each `<backupId>.manifest.json` records `createdAt`, `checksumSha256`, `sizeBytes`, `status`, and the exact repository migrations applied at backup time). Pick the most recent `"status": "SUCCESS"` manifest that predates the incident. **Do not select a `"FAILED"` manifest.**

### 3.3 Provision a clean recovery target

The restore target (`RESTORE_TARGET_DATABASE_URL`) must be empty or must not already hold live data — `npm run restore` refuses a non-empty-looking target by default (checks `reservations`/`staff_users`/`contacts` row counts) unless both `RESTORE_ALLOW_NON_EMPTY_TARGET=true` and `RESTORE_DISASTER_RECOVERY_CONFIRMATION="I UNDERSTAND THIS WILL OVERWRITE THE TARGET DATABASE"` are explicitly set — this override exists precisely for a real disaster where the only available target used to be the (now-lost) primary database and has since been recreated with the same name. Do not set the override casually.

### 3.4 Restore

```
npm run restore -- <backupId>
```

This applies the **repository's own migrations** (`prisma migrate deploy`) to the target first, then restores **data only** from the backup on top of that schema (architecture report §12's resolution: schema from the repository, data from the backup — never a dump's own embedded schema). Ephemeral security state (`staff_sessions`, `login_attempt_windows`) is deliberately **not** restored by default — see §8/AC-R14's documented decision — forcing a clean re-login and a clean rate-limit slate for everyone, which is the right posture after any disaster-recovery event.

### 3.5 Run integrity verification — mandatory, not optional

```
RESTORE_TARGET_DATABASE_URL=<target> npm run verify-integrity
```

**A successful restore command alone is NOT sufficient evidence of a working database** — this is the lesson this capability's own recovery drill directly demonstrated (an earlier version of the restore mechanism reported success while silently leaving `reservation_events` empty; only the integrity checker caught it — see the implementation report's evidence appendix). Do not proceed past a `FAIL` overall result.

### 3.6 Start the application and smoke-test

Point the application's `DATABASE_URL` at the restored database, start it (`npm start`), and perform a real, controlled smoke test: log in, view today's reservations, create one throwaway test reservation, confirm it appears. Do not declare recovery complete on the strength of the integrity checker alone — §14 of the architecture report requires an actual behavioral check too.

### 3.7 Declare the restored system authoritative

**Owner only.** This is an explicit, stated decision (verbally, in writing, however this team records such things) — not an inference from "the app seems to be responding." Once declared, proceed to §4.

## 4. Reconciliation After Outage

```
RECOVERY COMPLETE
  → Owner authorizes the restored system as authoritative (§3.7)
  → Manager gathers every manual outage-period record (§2.2)
  → Staff enters/reconciles outage-period reservations, modifications, and cancellations into the now-live system
  → Conflicts (e.g. a slot double-booked between the manual process and the last pre-incident system state) are reviewed manually — never auto-resolved
  → Duplicate detection (AppliedCommand-based idempotency) is advisory only during reconciliation entry — a staff member re-entering the same manual record twice by mistake is a real possibility this system cannot distinguish from two genuinely separate bookings without a human looking
  → Capacity rules apply normally again once entry is underway — no special "reconciliation mode" bypass exists or should be built
  → Reconciliation is verified (Manager/Owner spot-check against the manual paper record before closing it out)
  → Manual fallback is formally closed (Owner or Manager, once reconciliation is verified)
```

**Do not automatically replay handwritten/manual records without staff review** — every reconciled entry is a normal, individually-entered reservation/change, reviewed by the person entering it, not a bulk import.

## 5. Migration Safety (production schema changes, not disaster response)

```
BEFORE MIGRATION
  → verified recent backup exists (npm run backup, confirm SUCCESS manifest)
  → record current application commit (git rev-parse HEAD — already captured automatically in every backup manifest's applicationCommit field)
  → record current migration state (already captured automatically in every backup manifest's schemaMigrations field)
APPLY MIGRATION
  → prisma migrate deploy
  → run npm run verify-integrity against the post-migration database
  → start/verify the application
IF FAILURE
  → stop writes if the failure mode requires it
  → choose restore (§3) or a forward-fix migration based on what actually failed
  → do NOT write or execute a destructive down-migration — this project's migrations include hand-written CHECK constraints and partial unique indexes (see prisma/schema.prisma's own comments on CapacityCommitment/StaffUser) that Prisma cannot regenerate declaratively; a naive down-migration would not safely reverse them
```

The exact production scheduling/hosting for any of the above (§3's target provisioning, an automated pre-migration backup trigger) remains **HOSTING-DEPENDENT** — see the implementation report's own section on this. This runbook documents the sequence; it does not assume infrastructure that does not exist yet.

---

## 6. Reference — commands this runbook depends on

| Command | Purpose |
|---|---|
| `npm run backup` | Creates a `pg_dump` logical backup + manifest (checksum, size, schema state) in `backups/` |
| `npm run restore -- <backupId>` | Restores a backup into `RESTORE_TARGET_DATABASE_URL` (fail-closed on a non-empty target) |
| `npm run verify-integrity` | Runs the post-restore integrity checker (13 checks, PASS/FAIL) against `RESTORE_TARGET_DATABASE_URL` |
| `npm run service-snapshot` | Regenerates `snapshots/latest.html`/`latest.json` — see §2.1 |
| `npm run recovery-drill` | Full automated drill: seed → backup → restore → integrity → authenticate → smoke test, against disposable databases only — never the pilot's own `DATABASE_URL` |
| `npm run setup-test-db` | One-time provisioning of the integration test suite's sentinel-gated test database |

None of these commands push, deploy, or touch Guestplan or the Konnichiwa website.
