## EV-029 — Scenario A: Fresh Visitor, Google Consent Mode default state

  - `analytics_storage` = denied
  - `ad_storage` = denied
  - `ad_user_data` = denied

- **Relationship to earlier evidence:** confirms, with real browser-executed evidence, what EV-028 (O-014) inferred from static code reading of header.php's `gtag('consent','default',...)` call. - **Limitations:** which banner(s) were visually presented during this fresh visit (custom only, Complianz only, both, or neither) was not explicitly reported — this remains unconfirmed. No screenshot file accompanies this finding.

## EV-030 — Scenario D: Complianz Accept, resulting state

- **Source:** manual browser test, Kelvin, production `https://konnichiwa.nl/`, same session continuation, 22 August 2026, after clicking Accept in the visible Complianz consent interface only.
- **Collection method:** browser-executed observation per the Phase 1 protocol, reported as text.
- **Finding:**
  - Complianz cookies stored as allow.
  - `cmplz_event_marketing`, `cmplz_event_statistics`, `cmplz_event_preferences` fired (observed in dataLayer).
  - `konnichiwa_consent` (custom system's own localStorage key) remained `null`.
  - No `gtag('consent','update',...)` command was observed in dataLayer.
  - `google_tag_data.ics.entries` (Google's own internal, authoritative Consent Mode state object) showed:
    - `analytics_storage.default = false`, `analytics_storage.update = undefined`
    - `ad_storage.default = false`, `ad_storage.update = undefined`
    - `ad_user_data.update = undefined`
    - `ad_personalization.update = undefined`
  - No GA4 collect request was observed in the captured Network session.
- **Relationship to earlier evidence:** directly confirms, with live browser evidence, the gap that EV-026/EV-028 (O-014) established only through static/published-container inspection: no evidenced path converts a Complianz Accept action into a Google Consent Mode update. `google_tag_data.ics.entries` is a stronger form of evidence than a dataLayer log, since it reflects Google's own internal consent-state bookkeeping directly, not merely a list of commands issued.
- **Limitations:** exact timestamps, exact wait duration used, and full screenshot files were not supplied — only the summarized values above. Whether a longer wait (e.g. 30–60 seconds) might have produced a delayed update was not tested.
- **Confidence:** High for the reported values themselves; the underlying "why" (see diagnosis/HV-CSD-001…md) remains Medium-confidence pending authenticated Complianz configuration evidence.

## EV-033 — Confirmed live GTM double-loading

- **Source:** `https://konnichiwa.nl/` (public, unauthenticated HTTP GET), 22 August 2026.
- **Collection method:** direct HTML re-fetch and line-level inspection, in response to Case Owner instruction to check for duplicate GTM loading.
- **Findings:** **two independent GTM loader script blocks** are present in the live HTML, both targeting the identical container `GTM-WXH5P6SN`:
  1. The theme's own custom snippet in `header.php`, in `<head>`, loading unconditionally alongside the Consent Mode default-setting code.
  2. A second, separate block, explicitly preceded by the HTML comment `<!-- Statistics script Complianz GDPR/CCPA -->`, positioned near the end of the page body (after the Complianz cookiebanner script), wrapped in `<script data-category="functional">` — i.e., auto-injected by Complianz itself, corresponding exactly to EV-032's "Add Google Tag Manager: Yes" setting.
  - The `data-category="functional"` attribute is Complianz's own script-categorization mechanism; "functional"/"necessary" categories are, by common GDPR-plugin convention, typically exempt from consent-gating (unlike "statistics"/"marketing") — meaning this second GTM load likely executes unconditionally, regardless of any visitor consent choice. This interpretation is based on general Complianz/GDPR-plugin convention, not a direct authenticated confirmation of Complianz's internal blocking-rule engine.
- **Relationship to earlier evidence:** this is a genuinely new, separate technical finding — not a consent-propagation issue, but a duplicate-tag-manager-loading issue, confirmed live and independent of the consent-bridge question. It answers, directly, the Case Owner's explicit question: yes, GTM currently loads twice — once via the existing theme code, once because Complianz is configured to add it.
- **Limitations:** this confirms duplicate *script loading*; it does not by itself confirm duplicate *tag firing* inside GTM (that would depend on GTM's own internal deduplication behavior and tag trigger configuration, not independently verified here).
- **Confidence:** High for duplicate script-loading (directly observed, reproducible via public fetch); Medium for downstream consequences (duplicate tag firing / inflated GA4 counts) — plausible but not independently measured in this round.
