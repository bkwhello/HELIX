## EV-037 — Root-cause determination: event-target/bubbling mismatch

- **Source:** direct reading of the consent-bridge script block in EV-036's supplied production `header.php`.
- **Exact deployed implementation:**
  ```js
  (function () {
      function propagateConsent() {
          gtag('consent', 'update', {
              'analytics_storage': window.cmplz_has_consent('statistics') ? 'granted' : 'denied',
              'ad_storage': window.cmplz_has_consent('marketing') ? 'granted' : 'denied',
              'ad_user_data': window.cmplz_has_consent('marketing') ? 'granted' : 'denied',
              'ad_personalization': window.cmplz_has_consent('marketing') ? 'granted' : 'denied'
          });
      }

      window.addEventListener('cmplz_status_change', propagateConsent);
      window.addEventListener('cmplz_enable_category', propagateConsent);
      window.addEventListener('cmplz_revoke', propagateConsent);
  })();
  ```
- **Finding:** the three listeners are registered on `window`, using default `addEventListener` options (bubble-phase, non-capturing). Per the WHATWG DOM standard, a `Document` node's only ancestor in the event-propagation path is its associated `Window` — reachable by a `window`-level listener only in two cases: (a) the event's **bubble phase**, which requires the dispatched event to have `bubbles: true`, or (b) a **capture-phase** listener on `window` (`addEventListener(type, fn, true)` or `{capture:true}`), which does not require bubbling. `new CustomEvent('cmplz_status_change')`, constructed without an options object, defaults `bubbles` to `false`. Kelvin's own manual test (observations/O-016.md, EV-034, item 9) dispatched exactly this — `document.dispatchEvent(new CustomEvent('cmplz_status_change'))` — a non-bubbling event targeted at `document`. Under the propagation rule above, this event's path is target-only (`document`); it never reaches `window` in either the capture or bubble phase. The deployed `window.addEventListener(...)` registrations are therefore **structurally unreachable** by this dispatch — not due to timing, not due to Complianz's internal state, but due to the event target/bubbling mismatch between where the listener is attached (`window`) and where the event is targeted (`document`, non-bubbling).
- **Why this also explains the real-Accept-click failure, not only the manual test:** Complianz's own publicly documented third-party-integration pattern (referenced directly in the deployed code's own comment, `complianz.io/developers-guide-for-third-party-integrations/`) instructs integrators to listen via `document.addEventListener(...)`, consistent with Kelvin's own manual test target. If Complianz's real dispatch also targets `document` (as its own documented integration guide implies, and as the manual test was evidently modeled on), a real Accept click would hit the identical structural mismatch as the manual test — explaining why both produced the same symptom (all four `update` values `undefined`) rather than two separate defects.
- **Ruled out, by direct inspection of this same code:**
  - *`gtag` out of scope:* `gtag` is declared as a global function in the page's first `<script>` block, executed in document order before the consent-bridge block; by the time `propagateConsent()` can run, `gtag` is already defined globally. Not the cause.
  - *Guard/logic defect:* no conditional guard exists in `propagateConsent()` that could block execution — it runs unconditionally once invoked.
  - *Argument/key mismatch:* the four keys (`analytics_storage`, `ad_storage`, `ad_user_data`, `ad_personalization`) match Google's documented Consent Mode v2 signal names exactly, and match the same keys read by O-016/EV-034's DevTools inspection — a naming mismatch would not explain the symptom, since the function is never being invoked at all (per the finding above), not invoked-with-wrong-arguments.
- **Not ruled out — a separate, secondary, unconfirmed risk, distinct from the root cause above:** whether `window.cmplz_has_consent` exists under exactly that name at call time depends on Complianz's own script having defined it as a global by the time `propagateConsent()` runs — plausible per the code's own reasoning (Complianz's status-change events would only be dispatched after Complianz's own script has executed) but not independently confirmed here, since the root cause above already fully explains the observed symptom without needing this second risk to be present.
- **Confidence:** High. This is a direct reading of the actual deployed source (EV-036), not a hypothesis — the DOM event-propagation rule invoked is a stable part of the WHATWG DOM specification, not browser-specific or version-dependent behavior, and Kelvin's own manual test (EV-034, item 9) is itself the exact reproduction case this rule predicts.
