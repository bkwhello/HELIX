## EV-034 — Production validation results, Complianz→Google Consent Mode bridge

- **Source:** manual production test, Kelvin (Case Owner), `https://konnichiwa.nl/`, 23 August 2026.
- **Collection method:** browser-executed observation, reported as text, following a validation matrix that was stopped mid-run by Case Owner instruction on first confirmed defect.
- **Findings, in sequence:**
  1. Complianz "Add Google Tag Manager" confirmed **No** and saved (the GTM double-loading fix recommended alongside Option C in diagnosis/HV-CSD-001…md is confirmed applied).
  2. GTM-WXH5P6SN DOM script count = **1** (consistent with finding 1 — the double-load defect from EV-033/O-015 appears resolved).
  3. `dataLayer` `gtm.js` bootstrap count = **1** (same relationship).
  4. Before consent: Google Consent Mode correctly reports `default: false` for `analytics_storage`, `ad_storage`, `ad_user_data`, `ad_personalization`, with `update: undefined` — matches the intended pre-consent state.
  5. User clicked Complianz Accept.
  6. `cmplz_has_consent('statistics') === true`.
  7. `cmplz_has_consent('marketing') === true`.
  8. **Despite (6) and (7), all four Google Consent Mode entries still report `update: undefined`** — the update never reaches Google's internal consent-state object.
  9. Manually dispatching `document.dispatchEvent(new CustomEvent('cmplz_status_change'))` **also** leaves all four `update` values `undefined`.
  10. Production inspection (reported, not independently re-verified in this observation — see EV-035 for what could be independently verified) confirms a deployed inline bridge containing a `propagateConsent()` function and `gtag('consent','update',...)` logic is present on the page.
- **Relationship to earlier evidence:** this is the first production evidence that the Option C bridge design (diagnosis/HV-CSD-001…md, "Architecture Recommendation," Option C) was actually implemented and deployed. It also confirms the GTM double-load fix (EV-033) has been applied. However, it shows the bridge itself does not produce a working consent update — a new, distinct defect from both prior findings (Consent Mode V2 Premium-gating, GTM double-loading).
- **Why finding 9 is diagnostically significant:** dispatching `cmplz_status_change` manually on `document` is a direct, deterministic test that does not depend on Complianz's own internal firing behavior at all. If a correctly-registered `document.addEventListener('cmplz_status_change', propagateConsent)` (or equivalent) existed and executed without error, this manual dispatch should have produced the same `gtag('consent','update',...)` call as a real Accept click. That it did not isolates the fault to somewhere between "event received" and "gtag call executed successfully" — it rules out "Complianz never fires the event" as an explanation on its own.
- **Limitations:** the exact deployed source of `propagateConsent()` was not captured verbatim in this report (no view-source excerpt, no screenshot file supplied) — only its presence and non-functioning behavior. No browser console error/exception was reported as checked or absent; whether an exception was thrown and, if so, its text, is unconfirmed. Timing (whether a longer wait after Accept changes the outcome) was not tested.
- **Confidence:** High for the ten reported observations above, as reported. Not yet independently re-verified against production by this observation.

## EV-035 — Read-only repository and local-environment inspection, in response to EV-034

- **Source:** local file-system and git inspection only. No production access, no WordPress-admin access, no PageSpeed/CrUX/GTM/Complianz system accessed. Performed by Claude, 23 August 2026, in direct response to EV-034 and the Case Owner's read-only investigation instruction.
- **Collection method:** `grep`/`find` across the theme's git working tree (`Local Sites/konnichiwa/.../wp-content/themes/konnichiwa`) and `wp-content/plugins`, `wp-content/mu-plugins`; `git status`, `git diff`, `git log` on the theme repository (remote: `github.com/bkwhello/konnichiwa`).
- **Findings:**
  - `propagateConsent` does **not** appear anywhere in the theme's git-tracked working tree, in any committed history, or anywhere under `wp-content` on this machine (plugins, mu-plugins, or theme).
  - `cmplz_has_consent` and `cmplz_status_change` do **not** appear anywhere in the theme's files.
  - No Complianz plugin directory (`complianz-gdpr` or `complianz-gdpr-premium`) exists under this machine's local `wp-content/plugins` at all.
  - The theme's `header.php` (and a duplicate copy at `img/header.php` — pre-existing, not created by this task) contains only the **original custom, non-Complianz consent implementation** already documented in diagnosis/HV-CSD-001…md ("Current Consent Architecture," item 1): a hand-written `#cookie-banner`, `localStorage`-keyed on `konnichiwa_consent`, calling `gtag('consent','update',...)` directly from its own Accept/Decline handlers. No Complianz event listener, no `propagateConsent` function, no reference to any `cmplz_*` symbol exists in this file.
  - `git status` on the theme repository shows the working tree is ahead of `origin/main` by 2 local commits, with uncommitted modifications to `header.php` and nine other files — but `git diff header.php` shows those uncommitted changes are confined to the navigation/header-layout markup (logo placement, language switcher, sidebar removal) and do **not** touch the consent/GTM block (lines 1–311) at all. `git log --oneline -- header.php` shows only the repository's single initial commit ever touched this file.
- **Relationship to earlier evidence:** this is a new, structurally significant finding, independent of the functional bug reported in EV-034. **The `propagateConsent()` bridge that EV-034 confirms is deployed and running on production does not exist anywhere in this case's version-controlled source** (the theme's git repository, on this machine, in any commit or working-tree state) or in any locally-installed plugin. It was therefore added to production through a channel this investigation has no visibility into — most plausibly a direct production file edit outside this git repository, or a database-stored custom-code field (e.g. a "custom JS"/"header & footer scripts" plugin, or Complianz's own custom-code integration point), neither of which is captured by this repository or this local WordPress installation.
- **Consequence:** a static-code root-cause diagnosis of *why* `propagateConsent()` fails cannot be completed from this environment — there is no deployed-bridge source text available to read. Any root-cause explanation below this point is a ranked hypothesis based on the observed symptom pattern (EV-034), not a confirmed code-level finding.
- **Limitations:** this inspection covered only the local machine's git-tracked theme repository and locally-installed plugins. It does not rule out the bridge existing in a location outside this investigation's reach (e.g. directly on the production server's filesystem, outside git; the production database's options table; a plugin active in production but not installed in this local WordPress copy).
- **Confidence:** High — this is a direct, reproducible absence-of-evidence finding (grep/git across the full available local source), not an inference.
