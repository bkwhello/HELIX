## C. Existing Catering implementation

*Source: read-only inspection of the website repository `github.com/bkwhello/konnichiwa`, `main` at `41a88f8dc1a0fd6a0d78955ebaf952cf3b3f37c3`.*

**Observation:**

- NL template `page-catering.php` and EN template `template-catering-eng.php` both contain the Catering form (lines 224–247 in each).
- The form POSTs to `admin-post.php` with `action=konnichiwa_catering_inquiry`, a nonce, and the fields `cw_name`, `cw_email`, `cw_phone`, `cw_event_type`, `cw_message`.
- Server handler: `konnichiwa_handle_catering_inquiry()` (`functions.php`, lines 1189–1232). It verifies the nonce (`wp_die()` on failure), validates name, email and message, calls `wp_mail()` to `info@konnichiwa.nl`, and redirects to the referer with `?catering_inquiry=success` or `?catering_inquiry=error`.

**Limitation:** the Catering mail flow itself is **not** Production Verified; no Catering submission was made and no mailbox was inspected.

## D. Success-authority gap

**Observation:** the Catering success notice ("Bedankt voor uw aanvraag…", `page-catering.php` lines 224–226; EN equivalent in `template-catering-eng.php`) renders whenever the GET parameter `?catering_inquiry=success` is present. There is no server-consumed, one-time receipt comparable to the Private Dining mechanism (observations/O-025.md).

**Inference:** a visitor can reach the success-rendering state — via reload, bookmark or a typed URL — without the immediately preceding server submission having been accepted.

**Classification:** **measurement-authority gap.** It is not classified as a security vulnerability; no repository evidence supports that stronger classification.

## E. Analytics implementation gap

**Observation:**

- `catering_enquiry` appears only as `data-track` metadata: on the two "Vraag offerte aan" / "Request a quote" CTAs and on the `<form>` element in both templates, and on homepage links.
- No implemented JavaScript was found that converts `data-track="catering_enquiry"` into an analytics event; `build/catering.js` contains no tracking.
- No success-only `dataLayer.push` for `catering_enquiry` exists anywhere in the theme.

**Conclusion:** the website currently does not produce the required `catering_enquiry` success event. `data-track="catering_enquiry"` is metadata, not an analytics event.

- No functional `catering_enquiry` configuration: no Catering Custom Event trigger and no GA4 Catering event tag. The string `catering` occurs **zero** times in the inspected published `gtm.js`.

**Limitations:** the current GTM workspace was **not** inspected. Absence is established only for published Version 9 as inspected on 26 September 2026. GTM UI display names are not exposed by `gtm.js` and are not inferred.

## G. Production routing observation (separate)

**Observation (read-only GET requests, 26 September 2026):** `https://konnichiwa.nl/catering/` returned HTTP 301 (`x-redirect-by: Polylang`) to `/en/catering/`, including with a Dutch `Accept-Language` header; the resulting page was English (`lang="en-GB"`). The sitemap exposed `/en/catering/`; the Dutch homepage links to `/catering/`.

**Classification:** **routing/localization observation requiring later investigation.** Its cause is not diagnosed here. It is distinct from the analytics implementation gap in section E and from the success-authority gap in section D. No Polylang, WordPress or redirect change is proposed or authorised by this observation.

## H. Approved measurement semantics — Case Owner decision, 26 September 2026

`catering_enquiry` means **a server-accepted successful Catering enquiry**, aligned with the semantics of `private_dining_enquiry`.

It does **not** mean: a CTA click; form start; a submit attempt; a POST attempt; or an arbitrary page view carrying the success parameter.

This resolves the semantic question left open by the candidate taxonomy in observations/O-014.md (`catering_enquiry_click` / `_form_submit` / `_success`). O-014 is not rewritten; it remains historical evidence of the candidate taxonomy as it stood before this decision.

## I. Approved design direction — not yet implemented

The Case Owner approved **Option A** as design direction:

server-accepted submission → one-time server-controlled success state → success-only analytics event.

The Private Dining receipt mechanism (observations/O-025.md) is the architectural reference. The goal is semantic and success-authority consistency with `private_dining_enquiry`; it is **not** required that Catering copy every line or implementation detail of Private Dining. **No implementation has been approved, selected at code level, or started.**

## J. Future analytics contract (design level only)

- Event: `catering_enquiry`.
- Semantics: a server-accepted successful Catering enquiry (section H).
- The future `dataLayer` payload must contain no form PII.
- Design candidate only, by analogy with the existing `private_dining_enquiry` convention: fixed, non-personal values such as `enquiry_type: 'catering'` and `submission_status: 'accepted'`. Not implemented; not decided.
- No GTM trigger or tag for this event exists (section F).
